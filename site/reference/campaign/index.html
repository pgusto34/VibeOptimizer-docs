Campaign YAML

Every accepted campaign field, generated from the application model. Start with the campaign guide.

Reading defaults: these are literal schema defaults. An omitted optional block is not the same as an empty block. Fields inside a block are required only when that block/variant applies. Effective launcher behavior and cross-field rules are described below.

Complete campaign template

Section titled “Complete campaign template”

Replace illustrative image digests, model settings, paths and trusted commands before launching. This complete schema-3 template includes topology, budgets, bounded capture and recovery settings; see the field tables below to adapt it.

Conditions and effective behavior

Section titled “Conditions and effective behavior”
  • New automatic launches resolve optimization_backend to auto, infrastructure retries to 2, and total calibration captures to 1; these differ from the schema’s null defaults.
  • Campaign schema 3 requires topology, knowledge and stability. Schemas 1/2 retain their supported restrictions; selectable harness/image/turn/tool/context settings require schema 3.
  • mode: optimize requires the serving performance gate. Comparison requires actual after references in the case.
  • Component time budgets cannot exceed the campaign wall budget; per-attempt tokens cannot exceed the campaign token limit.
  • Registry images require immutable digests; local images follow the declared image contract.
  • Source paths follow POSIX patterns; protected paths take precedence.
  • Standard campaign examples use five serving pairs. The performance.repetitions field itself is required, not defaulted by the schema. Reducing it to two is an explicit test configuration.
  • An explicitly supplied infrastructure_retries: null is rejected; the model default null represents an absent setting, not a valid explicit retry count.
  • CLI overrides apply before freezing a new launch. Resume retains saved settings; missing historical execution/retry settings preserve historical behavior.
  • optimization_plan, preparation_receipt and preparation_identity normally come from the controller. They are not switches to bypass verification.
