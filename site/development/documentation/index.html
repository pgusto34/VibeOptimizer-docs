Maintain these docs

Build locally

Section titled “Build locally”

Use a current Node.js LTS supported by docs/package.json (Node 24 is suitable). Site builds do not install Python packages, start Docker, use GPUs or require provider credentials.

The default project base is /VibeOptimizer/; open that path in the local preview. Set DOCS_BASE and DOCS_SITE when building for another project URL. The same base must be used for build, link checks and preview.

Update references

Section titled “Update references”

The generator imports the current application input models, Typer command tree and exact pinned benchmark dependency in the normal authorized Python development environment. It never invokes a CLI callback or launches a campaign.

An existing authorized Python environment can be selected using DOCS_PYTHON; this is a documentation tool setting, not a campaign environment variable.

Generated tables, the API snapshot and their source-fingerprint manifest are committed. The static build verifies those fingerprints without importing Python or needing access to the private dependency. New source fields/options need descriptions in documentation-owned metadata; generation fails if descriptions are missing. Literal schema/parser defaults and effective launcher/historical behavior must be explained separately.

Author explanations, examples and cross-field conditions in the Markdown guides or documentation metadata. Do not change runtime validators, CLI definitions, campaign defaults or hashes just to improve prose.

Checks

Section titled “Checks”

Browser checks require Playwright’s Chromium installation. They run headless with GPU rendering disabled. The build checks relative links, rendered anchors and local assets under the configured base. External URLs are not fetched as a build requirement.

The Python generator regressions live under docs/tests/ and can be run using the project Python environment with unittest discover. A thin Python-only tests/test_documentation_reference.py adapter exposes them in the named core suite, without requiring npm or browser dependencies.

GitHub Pages

Section titled “GitHub Pages”

The application repository stays private. Its Documentation workflow checks pull requests and builds the site with DOCS_SITE=https://pgusto34.github.io and DOCS_BASE=/VibeOptimizer-docs. Only successful builds on main publish the static output to the public VibeOptimizer-docs repository. Manual workflow runs also publish only when main is selected.

The website is pgusto34.github.io/VibeOptimizer-docs. The public repository contains site/, its own Pages workflow and a README. It never receives the application’s Git history. Site updates replace only site/, remove obsolete pages and skip commits when nothing changed. The destination’s workflow and README are preserved. The public workflow uses its own GITHUB_TOKEN with Pages/OIDC permissions; the private workflow does not deploy Pages directly.

One-time setup

Section titled “One-time setup”
  1. Create public pgusto34/VibeOptimizer-docs with an independent Git history. Install docs/deployment/pages.yml as .github/workflows/pages.yml and use docs/deployment/README.md as its README. Bootstrap it with a verified static build under site/; the publishing workflow expects an existing main branch.
  2. In the public repository select Settings → Pages → Build and deployment → Source → GitHub Actions.
  3. Create a fine-grained personal access token, selecting resource owner pgusto34 and only VibeOptimizer-docs. Grant repository Contents: Read and write, leave all other optional permissions disabled and choose an expiration. The token does not need access to the private application repository or permission to modify workflows.
  4. In the private application repository, open Settings → Secrets and variables → Actions → New repository secret. Store the token as DOCS_PUBLISH_TOKEN. Enter it directly in GitHub; never put it in configuration, source or chat.
  5. Merge the publication workflow and run Actions → Documentation → Run workflow, selecting main, or push a documentation change to main.

The source workflow builds on Node 24 without Python dependencies, Docker, provider credentials or GPUs. The publication token is used only in the main-only publishing job, never in PR validation. Its checkout is authenticated only for the duration of that job. The public repository’s deployment workflow must be maintained separately; ordinary publications do not update it.

Verify and troubleshoot publication

Section titled “Verify and troubleshoot publication”

Check both workflows: Documentation in the private repository builds and pushes; Deploy documentation in the public repository publishes Pages. A green private workflow alone does not prove the public deployment completed. Check the homepage, navigation, search and configuration downloads after deployment.

If the publication credential is missing or expired, builds still run, but the publishing job fails with a setup message. Rotate the token by creating a new one with the same single-repository scope, replacing DOCS_PUBLISH_TOKEN, then revoking the old token. Rerun the private workflow on main.

For rejected pushes, check token permissions and destination branch rules. Do not broaden access to the private source repository. For deployment failures, confirm Pages uses GitHub Actions and the github-pages environment permits main. Rerun the public workflow to redeploy already-published files. If links/assets fail, verify the build’s DOCS_BASE matches the public repository name; a renamed repository or custom domain needs a corresponding build URL update.

Keep the site generic

Section titled “Keep the site generic”

Only curated content under the site content collection is published. Do not add experiments, run directories, coordination files, retained traces, credentials or machine-specific paths. Use portable templates and clearly label values the reader must replace. Historical validation reports belong outside the published source tree.
