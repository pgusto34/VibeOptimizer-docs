Progress & reports

Watch or detach

Section titled “Watch or detach”

By default the launcher follows campaign progress. Add --detach to submit and return:

Reconnect from another terminal:

Ctrl-C disconnects the viewer; it does not cancel detached work. The dashboard falls back to an event stream when the terminal cannot fit it. The event stream retains stage and budget updates. A labeled divider separates it from the live dashboard.

Read the dashboard

Section titled “Read the dashboard”

The framework/backend describes how optimization feedback is evaluated; execution location shows where the current stage is running. A simulation-backed campaign can temporarily be in a Slurm GPU capture stage.

Phase, stage, attempt and turn identify progress. Last stage update and worker heartbeat answer different questions: a live worker can legitimately spend a long time compiling or exporting without completing another stage.

Optimizer intent is a short public declaration requested within the existing optimizer call; it is not private reasoning or proof that an edit was applied. Missing intent does not change candidate acceptance. Verified source changes and measured/predicted results remain separately labeled.

Artifact reuse and retries are separate. Reuse should name the retained artifacts; a retry preserves the failed execution and starts another bounded execution of the same logical stage. Internal caches can be used even when no explicit artifact-reuse event is shown.

Queue and budget telemetry

Section titled “Queue and budget telemetry”

Pending GPU queue age applies only to pending Slurm jobs. Local CPU dispatcher waits are not GPU queue time. Campaign running time, current launch elapsed time, optimizer active time and token usage are different clocks/counters. New launches exclude confirmed stoppages from both campaign elapsed time and its enforced budget; ordinary GPU queues keep counting. Historical launches without a running-clock ledger retain their original deadline behavior.

In-flight model usage can be pending until the provider records it. Do not interpret pending as zero or add banked usage a second time when canonical accounting catches up. Unknown scheduler states remain unknown rather than becoming completion.

Storage and operational errors

Section titled “Storage and operational errors”

Storage errors should identify the affected filesystem/role, available capacity or inodes when known, stage and execution context. Docker storage may be on another filesystem from the run directory. A recovered readiness check can allow retry; it does not repair permission/configuration problems or grant new time.

An error message or final worker exit belongs in the retained logs even when the campaign later recovers. A terminal controller report is stronger evidence than a job disappearing from squeue.

Reports and evidence

Section titled “Reports and evidence”

ID-based commands use the configured campaign store. Reports reconstruct the decision from journal-bound evidence, including source/candidate identity, correctness, serving samples and acceptance thresholds. Timing supplements and dashboard projections do not rewrite the canonical verdict.

Keep generated source patches, logs, captures and reports in private run storage. They are not documentation assets and do not belong in the source repository.

The timing supplement groups recorded stage time under preparation, optimization by attempt/turn, and final validation. Reused preparation and missing timing intervals are named explicitly. Optimization used remains the current attempt’s accumulated optimizer usage during validation; it is not a validation timer. The latest completed result identifies its attempt.

Roofline summaries

Section titled “Roofline summaries”

After baseline or candidate analysis, a bounded table shows the five most expensive individual profiled operations, their sampled case/window, available roofline diagnosis, coverage warnings and full-analysis reference. These costs are not whole-workload runtime percentages. Each analysis table prints once while following; status shows the latest and the supplemental timing report retains their history. The viewer reuses existing analysis without new capture or simulation.
