Preparation & reuse

Preparation turns a configured serving case into reproducible optimizer inputs. It is performed before optimizer turns, and compatible verified work can be reused.

The normal path

Section titled “The normal path”
  1. Resolve the case, model, engine/harness images, workload, hardware and launch settings.
  2. Build or reuse patched VibeSim binaries in a CPU-only container.
  3. Acquire a Slurm GPU allocation, validate its devices in that allocation, and capture representative workload execution.
  4. Export graph cases and measured operation profiles on local CPUs.
  5. Run CPU simulation and roofline analysis; publish predictions, analysis/API evidence and a preparation receipt.
  6. Enter the optimizer loop unless --prepare-only was requested.

Default preparation does not require every possible alternative kernel to be profiled in advance. Candidate edits can extend coverage later through adaptive GPU evaluation.

Device checks share the capture allocation rather than requiring a separate GPU preflight job. Normal preparation proceeds from prediction and roofline publication to the optimizer; early reference-correctness and rebuild checks are optional strict work. Independent candidate correctness and serving checks remain part of final validation.

Representative capture

Section titled “Representative capture”

New launches default to bounded capture: a deterministic request cohort, complete prefill execution, and up to eight total complete decode iterations spread across generation progress. Short generations merge overlapping windows. The engine executes between windows without detailed activity tracing.

Each window has its own graph and work metadata. Analysis keeps window-specific context and diagnostics, alongside the aggregate sampled-cost feedback. Sampled GPU cost is not full serving latency or a substitute for the final serving benchmark.

Explicit mode: full retains full capture when desired. A retained preparation keeps its frozen sampling/repetition policy when resumed. New profiling captures use one workload repetition by default; final serving uses its independent configured repetition policy.

Resume preparation

Section titled “Resume preparation”

Continue the same run directory to reuse its verified completed stages:

A partial capture is not treated as complete. After an explicit retry, compatible completed GPU gates may be reused, while an interrupted capture is collected into a fresh output directory. Failed evidence remains retained.

Reuse a completed receipt

Section titled “Reuse a completed receipt”

The campaign model supports explicit receipt reuse:

Use the receipt path and identity actually published by preparation; do not guess them from a directory name. Let normal preparation resolve the rest of the configured inputs. The controller verifies compatibility and artifact contents before consuming reused work.

Compatibility includes source/image/model identities, workload and engine settings, GPU contract, capture policy, simulator/observer inputs and relevant implementation identity. Matching only the case ID or compute capability is insufficient.

Reusing preparation can retain its original artifact locations. Keep the original receipt, frozen checkout and referenced files available. The controller verifies the recorded image inventory and access derivation instead of requiring them to be manually copied into the new run. Runtime images with different commit metadata are reusable only when their immutable filesystem layers, complete configuration and platform match.

A compatible raw capture can be retained when CPU export or publication processing changes. The controller creates a new identity-bound CPU output and verifies reuse; it does not relabel or overwrite the original export. Changed source, workload, sampling policy or hardware can still require a new GPU capture.

A binary cache, model cache, native build cache and completed preparation receipt reuse different amounts of work. Reusing a compatible simulator binary does not mean captures or predictions are reusable. A zero dashboard artifact-reuse count also does not establish that internal caches were unused.

Optional qualification

Section titled “Optional qualification”

--simulation-fidelity freezes predictions and checks fresh independent GPU measurements. Its qualification gate requires complete profile coverage and at most 10% duration-weighted absolute error separately for prefill and decode. This is optional; ordinary preparation need not run held-outs before publishing analysis.

--independent-verification is a separate strict reconstruction/preflight policy. In normal non-strict preparation, supported incomplete-capture conditions can be published with explicit warnings and unqualified predictions. Missing measured timings are not assigned invented zero cost. Final GPU acceptance remains independent.
