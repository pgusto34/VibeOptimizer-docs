Build & preparation recipes

There are two different recipe contracts. They are intentionally separate:

RecipeLocationResponsibility
Source-buildReferenced by case.yaml → architectures.<architecture>.recipeWhich packages/source paths may change, how installed imports bind to source, and which build backend handles edits
PreparationOptional campaign.yaml → preparation.recipeHow to create reusable campaign inputs, capture execution, publish analysis and receipts

Download the reusable vLLM recipe or SGLang recipe.

Source-build recipes

Section titled “Source-build recipes”

Prefer schema 2. VibeOptimizer ships reusable vLLM and SGLang source-build examples in examples/build-recipes/. Copy the appropriate file into the case directory as recipe.<architecture>.yaml (for example, recipe.9.0.yaml) and adapt its paths to the pinned engine image.

A vLLM recipe may include:

Python-only edits can use overlays. Native source, headers and package build metadata select the relevant package build path. For SGLang, declare the Python package and sgl_kernel binding/build backend separately as needed. The engine must contain its declared build dependencies.

A recipe does not guarantee a cheap cold compilation. Retained build outputs, dependency caches and compiler caches must be compatible with the candidate, toolchain and image. Warm builds avoid redundant work; missing or incompatible native outputs may require real compilation.

Generic discovery captures actual execution and prepares graph/profile inputs. It does not require a catalog of RMSNorm alternatives. During optimization, new source changes can request additional measured evidence through the adaptive controller.

Compatibility paths

Section titled “Compatibility paths”

Current launches require generic-serving preparation with capture-based discovery and adaptive candidate profiling. Case-specific adapters, descriptor-based simulator producers and fixed-alternative catalogs are retired for execution. Their retained reports, receipts and serialized fields remain readable and verifiable; parsing a historical field does not enable its old execution path.

Use the original pinned checkout to execute or resume a retired workflow. A compatible current capture-based campaign can resume in its frozen checkout; upgrading its implementation while it is active is not a supported checkpoint migration. Schema-1 step records remain readable for historical verification and internal preparation bookkeeping.

Preparation fields lists every accepted recipe field. Preparation and reuse explains receipts and cache boundaries.
